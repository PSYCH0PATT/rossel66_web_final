## A. Даты и форматирование

- **A1 (корень).** `Release.releaseDate` — `String` в ДВУХ форматах: `"DD.MM.YYYY"` (парсеры koala/zvonko) и `"YYYY-MM-DD"` (форма добавления — native date-input, месяц-первый «мм/дд/гггг»). Источник всех date-багов.
- **A2. Непоследовательная сортировка релизов.** `/api/releases:115` — по `releaseDateSort` (верно); но `lib/cached-dashboard.ts:384,563` и `lib/storage.ts:187,459,482,501` — по `createdAt` (порядок добавления). `app/api/excel/[artistId]/route.ts:27` — строковый `releaseDate desc` → из-за смешанных форматов порядок неверный.
- **A3. `releaseDateSort` частичный.** Ставится при create/update, но старые/непарсящиеся → `null` → при `desc` NULLS FIRST всплывают наверх. Backfill — ручной.
- **A4. «Invalid Date» / английские даты на клиенте.** Голый `new Date(releaseDate)`: `releases-client.tsx:219` (главный список — показывает «May 14, 2026» на русском UI!), `artist/[username]/page.tsx:200`, `admin/artists/[id]/releases/page.tsx:166`, `excel/[artistId]:38`. Для формата DD.MM.YYYY → «Invalid Date». Корректные образцы: `releases/[id]/page.tsx:122`, `admin-releases-client.tsx:226`.
- **A5. Даты плейлистов — строки в UTC.** `firstSeenDate/lastSeenDate` пишутся `new Date().toISOString()` (`sftp-playlist-storage.ts:88`), а пайплайн ключует по МСК → сдвиг дня 21:00–24:00 МСК. Отображается сырой ISO (`playlists/[id]/page.tsx:59,120`). См. также **A11 [feedback]**.
- **A6. `uploadedAt` vs `uploadDate`.** Сортировка по `uploadedAt` (верно), отображение по nullable `uploadDate`; null → `new Date(null)` = «01.01.1970» без guard в `admin/artists/[id]/page.tsx:729`, `reports-list.tsx:435`, `unregistered-reports-list.tsx:223`, `artist-reports.tsx:173`, `excel:38`.
- **A7. Календари аналитики сдвигают диапазон на −1 день.** `customStart.toISOString().split("T")[0]` (`admin/analytics:195`, `artist/analytics:110`) для локальной полуночи МСК → запрос на день раньше, label показывает верную дату. Есть `mskDateString()` — не используется. Preset-диапазоны так же.
- **A8. X-ось графиков.** `new Date("YYYY-MM-DD").getDate()` — для зрителей западнее UTC предыдущий день.
- **A9. Мёртвый `generatedDate`.** `artist-reports.tsx:170` — поля нет в схеме → «Сгенерирован:» никогда не рендерится.
- **A10. История плейлистов.** `lib/playlist-history.ts:44` всегда `[]` → таблица пуста; `change_date` (date-only) показывается с временем «03:00».
- **A11. ⚠️[feedback] Дата «первого появления» плейлиста нестабильна.** Пользователь: дата плейлиста постоянно обновляется даже при нахождении того же плейлиста; должна быть дата ПЕРВОГО появления и не меняться. Разбор `sftp-playlist-storage.ts:61-141`:
  - В БД `firstSeenDate` при `update` **не перезаписывается** (данные сохраняются). Карточка показывает `added_at = first_seen_date` (`/api/playlists/sftp:137`).
  - НО (1) список сортируется `orderBy updatedAt desc` (`:215/249/274`), а `updatedAt` бампается на каждом прогоне для «изменённых»; из-за бага `label` (**F6**) `tracksChanged` (`:93`) **всегда true** → каждый прогон бампает `updatedAt` + спамит `recordPlaylistChange('updated')` → плейлисты постоянно всплывают/переупорядочиваются, а история засоряется.
  - (2) `findFirst` матчит по `(playlistUrl, playlistName, artistName)` (`:80`). Разное написание `artistName` в CSV между прогонами → совпадение не найдено → создаётся **новая строка с `firstSeenDate=сегодня`**, старая устаревает → «первое появление» фактически сбрасывается.
  - **Фикс:** матчить плейлист по стабильному ключу (в первую очередь `playlistUrl`), при слиянии дублей брать МИНИМАЛЬНЫЙ `firstSeenDate`; ~~починить `label` (F6)~~ ✅ **сделано** (коммит 27d72d8) — `tracksChanged` больше не всегда true; **осталось:** сортировать список по `firstSeenDate` (а не `updatedAt`) и предотвратить создание дублей-строк при вариации написания `artistName`. Оба — в рискованном `sftp-playlist-storage.ts` (тот же файл, что и B3), делать аккуратно отдельно.

## B. Фиты и коллабы (главная жалоба)

- **B1. Фит-артист не видит свой релиз.** `cached-dashboard.ts:381-387` фильтрует `where:{artistId}` только по основному; `/api/releases:63-98` не использует `featuredArtistIds`. Гость не видит релиз, админ не может отфильтровать по гостю.
- **B2. Админ-аналитика: дубли + «съедание» стримов.** `flash-storage.ts:323-369` `getAvailableArtists` группирует по сырому `trackArtist` → «Artist» и «Artist feat Guest» две записи; коллаб 2 ростер-артистов → `resolveArtistId=null` → отдельная unmapped-запись; выбор «Artist» НЕ включает фит-стримы (занижение). UI: `admin/analytics:416-434,61-67`.
- **B3. Админ-плейлисты — те же дубли.** `admin/playlists:776-782` `getUniqueArtists` и «по артистам» (1347) из сырого `artist_name`; фильтр сервер `find(name===)` vs клиент `includes` рассинхрон.
- **B4. Кабинет артиста — митигация хрупкая.** `playlist-artist-match`/`analytics-artist-match` токенизируют коллаб (гость видит), но только пока `artistId==null`; после привязки к одному участнику второй теряет видимость.
- **B5. Track-дропдаун** — сырой коллаб `trackArtist` на трек; фильтр — точное совпадение.

## C. Расчёты, агрегации, ПРОСЛУШИВАНИЯ

- **C1. ⚠️[feedback] Категории `length` — их ЧЕТЫРЕ, платный тир недосчитан.** Реальные значения в CSV: `Полный стрим` (4749), `Платный стрим (30+ сек)` (3267), `6-29 сек` (3551), `0-5 сек` (3701). Код `flash-storage.ts:216,258`: `isPaid = length==='Полный стрим' || 'full'` → **`Платный стрим (30+ сек)` (буквально «Платный») уходит в «Бесплатные»**. ~40% платных теряются.
  - **Фикс (решение пользователя, п.3): ДВЕ категории.** Платные = {`Полный стрим`, `Платный стрим (30+ сек)`}; бесплатные = {`6-29 сек`, `0-5 сек`} (т.е. всё 0–29 сек). Реализовать case-insensitive классификатором `length` в одном хелпере (напр. `isPaidStreamLength(length)`), переиспользовать в `paidVsFree` и per-track. Третью категорию НЕ вводить — оставить график/разбивку «Платные vs Бесплатные».
- **C2. ⚠️ Двойной счёт стримов.** `buildStreamAnalyticsWhere:127-152` не фильтрует `isMonthlyAggregate` → groupBy суммируют дневные И месячные строки. Штатно ОК (агрегация удаляет дневные), но `createMany`+`deleteMany` (`:470-492`) не атомарны: сбой между ними → постоянный ×2. Плюс месячный агрегат (дата=1-е число, локальная TZ) рисует месяц одним всплеском.
- **C1b. ⚠️[feedback] «Прослушивания» включают скипы → расходятся с DSP.** Разбор пути (ответ на п.4): вставка корректна (`saveFlashRecords:27-103` — стримы 1:1, без масштабирования; дедуп по `date|isrc|dsp|length|source` + `skipDuplicates`; CSV строго per-day, пересечение ключей между файлами = 0 → повторный импорт не задваивает). НО `streamsByTrack`/`streamsByDay`/`totalStreams` (`flash-storage.ts:161-265`) суммируют ВСЕ категории `length`, включая `0-5 сек` (3701) и `6-29 сек` (3551) — то есть **скипы/превью считаются прослушиванием**, тогда как Яндекс/VK обычно считают стримом только 30+ сек. Отсюда цифра в кабинете ВЫШЕ, чем на площадке.
  - **Итог по п.4 «наша это проблема или нет»:** и то, и другое. Определение «что есть прослушивание» — бизнес-решение (включать ли <30с). Но конкретные баги нашей стороны, искажающие цифру: **C1** (платный/бесплатный неверно), **C2** (возможный ×2 на истории), **A7** (TZ-сдвиг границы диапазона включает/исключает крайний день). Рекомендация: определить «прослушивание» как Полный+30+ (как деньги), либо явно показывать total с разбивкой по категориям, чтобы совпадало с отчётом DSP.
- **C3. `percentage` — два процессора.** Python (`python-report-processor.py:547-604`, прод) применяет (нетто). TS `report-processor.ts` — мёртвый, процент не применяет (латентный риск брутто). Крайние: 0%→сумма 0; битый→100% (переплата); пустой→артист пропущен.
- **C4. Дедуп-расхождение баланса.** Админ-дашборд дедуплицирует отчёты (`cached-dashboard.ts:205-213` по `quarter|year|artistName`), а `getArtistBalance`/`totalEarnings`/`/api/payments` — нет → дубли завышают баланс артиста; ключ по `artistName` схлопывает тёзок.
- **C5. Метки KPI и фейковые дельты.** «Заработок» = все начисления (не «доступно»); админский «Выплаты» = оплаченные+неоплаченные. Дельты `+5.4%`/`+1`/`+2`/`+4` захардкожены.
- **C6. Формат сумм.** `format-dashboard-rub.ts` `Math.max(0,n)` прячет минусы; 1500 → «2K».
- **C7. totalPlays коллабов** прибавляется полностью каждому артисту — суммировать по артистам нельзя.
