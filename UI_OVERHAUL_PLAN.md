# ROSSEL MUSIC — план полной переработки фронта (UI-система + CRO)

Роадмап для выполнения в Claude Code. Каждый этап = отдельная сессия (или несколько), не смешивать этапы в одном чате — именно из-за смешивания большой аудит «ничего не дал». Скриншоты — единственный ground truth, код на глаз не оценивать.

**Ключевой факт про проект:** shadcn/ui уже стоит (`components/ui/` — button, card, dialog, tooltip, table и т.д., есть `components.json`). Дизайн-систему НЕ строим с нуля — проблема в том, что страницы её не используют и верстают всё заново. Значит план: токены → доукомплектовать систему → запретить обходить её → пересадить страницы волнами.

---

## Скоуп

Только личные кабинеты: `app/dashboard/admin/*` и `app/dashboard/artist/*` (+ логин). Лендинг, формы, FAQ, distribution, guide — НЕ трогаем вообще: не аудитим, не мигрируем, не скриним.

## Скиллы, которые ставим до старта

```bash
# Аудит UI-кода по гайдлайнам Vercel (a11y, формы, responsive, фокус) — вывод file:line
npx skills add vercel-labs/agent-skills --skill web-design-guidelines

# UX-аудит по скринам: эвристики Нильсена, IA, когнитивная нагрузка; есть профиль под дашборды/админки
# https://github.com/wonjyou/design-audit → SKILL.md в .claude/skills/design-audit/
```

Плюс design-review workflow (агент со скриншотами через Playwright MCP):
`https://github.com/OneRedOak/claude-code-workflows` → скопировать `design-review/` агент и slash-команду в `.claude/`.

**CRO для ЛК:** готового скилла под дашборды в экосистеме нет (всё «CRO» — про лендинги). Поэтому используется кастомный скилл `lk-cro` (лежит в `.claude/skills/lk-cro/SKILL.md`): job экрана → опись элементов → PRIMARY/SECONDARY/RARE/DEAD → правила размещения → friction-чек → вердикт-таблица. Отдельные цели для админа (скорость оператора) и артиста (ясность для гостя).

Скиллы модель-агностичны — «под Fable 5 / Opus 5» отдельных не существует, работают с любой моделью. Важно содержание, а не совместимость.

## Этап 0 — Страховка (чтобы ничего не поплыло). ~1 вечер

0.1. Ветка `redesign/design-system`. Всё смотрим только через Vercel preview, staging не трогаем до конца этапа.

0.2. **Visual baseline.** Playwright уже настроен (`playwright.config.ts`). Написать скрипт: логин → обход всех роутов ЛК (админ + артист, публичные не нужны) → скрины 1440px и 390px → в `screens/baseline/`. Ключевые состояния тоже: открытый тултип графика, модалки, фильтры, пустые состояния. Это эталон, с которым сравнивается каждая волна.

0.3. **e2e smoke** на критичные флоу, если их нет: логин, добавить релиз, добавить артиста, загрузка отчёта, открытие аналитики. Зелёный smoke = функционал жив.

Промпт для Claude Code: «Напиши Playwright-скрипт visual-baseline: залогинься под админом и под артистом, обойди все роуты из app/dashboard, сними скриншоты 1440 и 390, сложи в screens/baseline/{route}/{viewport}.png. Ничего в приложении не меняй.»

## Этап 1 — Инвентаризация и аудит (только чтение, ноль правок)

1.1. **UI-инвентаризация.** Агент проходит по коду и собирает: сколько уникальных вариантов кнопок/инпутов/заголовков/карточек живёт вне `components/ui` (raw `<button>`, ad-hoc классы). Выход — таблица: паттерн → где встречается → каким компонентом заменить. Это и есть твой список «кнопки не реюзаются», превращённый в чек-лист миграции.

1.2. **web-design-guidelines** прогон по всем страницам → список нарушений file:line.

1.3. **Design-review по скринам** из baseline: отступы, разъехавшиеся заголовки, тултип стримов, mobile-косяки. Каждая находка: экран + скрин + тип (консистентность / responsive / шум / иерархия) + severity.

1.4. **Кластеризация** — главный шаг, которого не было в прошлом аудите: свести находки к системным причинам. Ожидаемо ~80% сведётся к 10–15 пунктам уровня «нет единого PageHeader», «нет единого Toolbar», «тултип чарта без max-width и мобильного поведения».

Выход этапа: `docs/ui-audit.md` — бэклог, кластеризованный и приоритизированный.

## Этап 2 — Дизайн-система (ВАЖНО: без визуальных изменений)

2.1. **Токены.** Выпарить из `globals.css` (51КБ!) и `tailwind.config.js` реально используемые значения → свести к шкалам: spacing, радиусы, типографика, цвета (тёмная тема). **Правило «не поплывёт»: на этом шаге токены = текущим значениям.** Сайт после этапа 2 выглядит ТАК ЖЕ. Менять значения (красивее/чище) — отдельный осознанный шаг после, когда всё сидит на токенах и меняется в одном месте.

2.2. **Доукомплектовать компоненты** поверх существующего shadcn:
- `PageHeader` — breadcrumb + заголовок + subtitle + actions (лечит разные отступы на Артистах/Релизах навсегда)
- `Toolbar` / `ActionBar` — primary-действие + secondary в dropdown (лечит свалку кнопок на Релизах)
- `StatCard` — карточки «Всего / Подтверждены / Новые»
- `ChartTooltip` — max-width, компактный, на mobile — фиксированная панель ПОД графиком, не поверх
- `EmptyState`, `PageSection`, обёртка `DataTable`
- `ui/button.tsx` расширить вариантами и объявить единственной легальной кнопкой

2.3. **Витрина `/dev/ui`** — одна страница со всеми компонентами во всех вариантах. Проверять систему глазами в одном месте, сюда же смотрит каждая следующая сессия Claude Code как на референс.

2.4. **(Опционально) Claude Design.** Проект туда заводить не нужно. Использовать как генератор референса: собрать эталонный вид 2–3 ключевых экранов (дашборд, релизы, аналитика) в твоей стилистике, утвердить визуальный язык, перенести решения в токены/компоненты руками Claude Code. Дизайн-направление сначала, миграция потом — не наоборот.

## Этап 3 — Enforcement (чтобы это не повторилось)

Делается ДО миграции, не после — иначе пока переносишь старые страницы, новые генерации снова плодят кнопки.

3.1. **ESLint:** `no-restricted-syntax` — запрет raw `<button>`/`<input>`/`<select>` вне `components/ui`; запрет arbitrary-цветов в className (`bg-[#...]`).

3.2. **AGENTS.md** (он у тебя уже есть) — дописать раздел «UI-правила»: любые UI-элементы только из `components/ui`; каждая страница дашборда начинается с `PageHeader` + `Toolbar`; ни строчки нового CSS в `globals.css`; перед изменением UI смотреть `/dev/ui`. Cursor и Claude Code читают этот файл — это страховка от будущего расползания.

---

## Этап 4 — Миграция волнами

4.1. Порядок: от простых к сложным. Сначала мелкие страницы (reports ~5К, activity), в конце монстры (`playlists/page.tsx` 65КБ, `analytics` 43КБ, `artists/[id]` 42КБ). Первая волна — обкатка процесса.

4.2. **Одна волна = 2–4 страницы = один PR.** Промпт каждой волны обязательно содержит: «Только представление. Не трогай API-вызовы, состояния, данные, роутинг. Используй только components/ui, PageHeader, Toolbar. Сверяйся с /dev/ui.»

4.3. После каждой волны: скрины тех же роутов → сравнение с baseline (pixelmatch/odiff или просто отдать Claude пары до/после) → все отличия должны быть намеренными; e2e smoke зелёный; глазами пройтись по preview на телефоне.

4.4. Мерж волны → следующая. Никогда не держать 10 страниц «в полёте» одновременно.

## Этап 5 — CRO ЛК / убрать хаос (скилл `lk-cro`)

После стабилизации системы, отдельными волнами — не вперемешку с миграцией.

5.1. **Подготовка:** для каждого экрана выписать топ-3 реальные задачи и частоту («каждый день / раз в квартал») — это твой инпут, скилл без него не работает и не должен гадать.

5.2. **Админ-ЛК, экран за экраном:** прогон `lk-cro` по скринам из baseline. Цель — скорость оператора: одно primary-действие + одна главная метрика на экран, RARE-операции (парсеры, bulk, привязки, экспорт) — в dropdown «Импорт»/«Ещё», DEAD — удалить. Выход: вердикт-таблица keep/demote/move/kill на каждый экран.

5.3. **Артист-ЛК, экран за экраном:** тот же прогон, но цель — ясность для гостя: главные цифры за 5 секунд, ноль внутреннего жаргона (парсеры/UPC/привязки не должны существовать в мире артиста), внятные empty states для новичка без релизов.

5.4. Все решения — в `docs/ia-decisions.md` (журнал, чтобы следующие сессии не перерешивали). Внедрение — волнами по 2–4 экрана, как в этапе 4, с visual diff.

## Этап 6 — Финал

Полный повторный скрин-прогон desktop+mobile → финальный design-review → добить остатки бэклога из этапа 1 → обновить baseline (теперь он = новый эталон для будущих фич) → мерж в staging.

## Правила максимального результата (почему прошлый аудит не сработал)

1. Один этап = одна сессия. Не просить «проанализируй весь фронт» — просить конкретный шаг конкретного этапа.
2. Скриншоты — ground truth. Любая оценка UI только по скринам, любая проверка правок — сравнением скринов.
3. Сначала система и enforcement, потом миграция, потом CRO. Перестановка порядка = сайт плывёт.
4. Токены сначала копируют текущие значения (visual no-op), меняются потом одним местом.
5. Только представление, логику не трогать — писать это в каждом промпте волны.
6. Волна не мержится без: visual diff проверен, smoke зелёный, mobile посмотрен руками.
