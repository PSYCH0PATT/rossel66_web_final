## 0. Как читать этот файл

- **P0** — ломает функцию целиком ИЛИ дыра в доступе/безопасности. Чинить в первую очередь.
- **P1** — работает нестабильно / часть кейсов сломана / данные расходятся.
- **P2** — риск на будущее / тех.долг / UX.
- Пометка **[LIVE]** — воспроизведено вживую на работающем приложении, не только по коду.
- Пометка **[env?]** — критичность зависит от прод-окружения (Timeweb), которое мне недоступно; нужно проверить руками.

## 1. Резюме: общее состояние

Кабинет **функционирует в основных сценариях чтения** (логин, списки артистов/релизов/выплат, дашборды рендерятся, API отдают данные), но содержит **несколько дыр в безопасности уровня P0, доступных без авторизации**, и целый пласт «наполовину рабочих» функций записи (аватары, смена пароля админа, кнопки очистки/удаления в парсерах), а также системный рассинхрон данных и кэша.

Первопричины сгруппированы в §3 — почти все проблемы растут из 4–5 общих корней, а не независимы.

### Топ-5 проблем (чинить первыми)

1. 🔴 **[LIVE] Бэкапы БД доступны без авторизации.** `GET /api/backups/download?id=…` без cookie отдаёт zip (проверено: 200, 740 КБ) с `users.json`, где все пользователи **и пароли**. id бэкапа = `Date.now()` — перебираемый. `POST /api/backups/restore` и `POST /api/backups` тоже без `requireAdmin`. Это неаутентифицированная выгрузка всей БД + удалённое разрушение данных restore-ом. → **F-SEC-1**
2. 🔴 **[LIVE] Куки-сессии VK/Bandlink утекают без авторизации.** `GET /api/vk/cookies` и `/api/bandlink/cookies` без auth отдают `name=value` сессионных cookies (POST/DELETE защищены, GET — нет). → **F-SEC-2**
3. 🔴 **Подделка admin-сессии без `AUTH_SECRET`.** Legacy-режим принимает неподписанный `base64(JSON)` cookie → любой формирует `role:"admin"`. **Локально `AUTH_SECRET` не задан** (есть только в `.env.example`) — значит локально сессии уже неподписанные; на проде **нужно срочно проверить**, что `AUTH_SECRET` задан. → **F-SEC-3**
4. 🟠 **Записывающие функции кабинета «наполовину» сломаны:** смена аватара (артист и админ) всегда падает (base64 против `avatarUrl.max(2000)`); смена пароля админа невозможна в принципе (сверка с полем, которого API не отдаёт); кнопки «очистить/удалить» в парсерах бьют в несуществующие таблицы/не то хранилище. → **F-UI-1..4**
5. 🟠 **Рассинхрон данных и кэша:** [LIVE] 8 из 20 artistId в выплатах — осиротевшие (артист не видит свои деньги); мутации paid/signed и acknowledge не инвалидируют кэш → цифры расходятся до 10 минут; связи без FK. → **F-DATA-1..3**, **F-CACHE-1..2**

### Здоровье инструментов качества (всё выключено)
- `next.config.mjs`: `typescript.ignoreBuildErrors: true` + `eslint.ignoreDuringBuilds: true` → **реальные ошибки типов и линта уезжают в прод**. `tsc --noEmit` даёт 6 ошибок (5 в коде кабинета).
- **ESLint де-факто не запускается**: конфиг `eslint.config.mjs` (flat, для ESLint 9), а установлен ESLint 8.56 → `next lint` уходит в интерактив, `eslint` не находит конфиг. Статанализ никогда не отрабатывал.
- **Тестов на кабинет ~0**: 16 зелёных тестов покрывают только `lib/pyrus-catalog/*` и `analytics-artist-match`. Роуты, auth, релизы, отчёты, выплаты, UI — не покрыты.
- **Нет error-boundaries**: ни одного `error.tsx` / `global-error.tsx` / `not-found.tsx` — любая необработанная ошибка рендера показывает голый экран Next.

## 2. Инфраструктура и деплой (важно для оценки критичности)

**Деплой — долгоживущий Docker-контейнер на Timeweb, НЕ Vercel serverless.** Подтверждено: `Dockerfile` (Node 20 alpine + Python + Chromium), `entrypoint.sh` (`prisma migrate deploy` → `crond` → `next start`), системный `crontab` (парсеры и SFTP через `curl` на `127.0.0.1:3000` с `Bearer $CRON_SECRET`).

**Следствие для оценки:** ряд находок агентов, критичных «на Vercel» (эфемерная ФС для SQLite, `spawn(python)` невозможен, in-memory rate-limit бесполезен, лимиты `maxDuration`), на одном постоянном контейнере **работают** и понижены в критичности. Но связанные с ними **логические баги остаются** (кнопки бьют не в ту таблицу, одиночный контейнер = single point, статус парсера может «зависнуть»).

**Сделано в рамках этой сессии (по прямому запросу — убрать Vercel):**
- удалён `vercel.json` (cron-конфиг дублировал системный `crontab`);
- убраны мёртвые ветки `process.env.VERCEL_URL` в `lib/scheduler.ts`, `app/api/cron/{koala,zvonko,playlists}/route.ts` (поведение не изменилось — на Timeweb переменная не задавалась, резолв всегда шёл в `NEXT_PUBLIC_BASE_URL` → `localhost:3000`);
- переписаны `README.md` (Timeweb/Docker вместо Vercel-boilerplate), `SECURITY.md` п.3, коммент в `lib/cron-auth.ts`, демо-строка в `components/kokonutui/list-02.tsx`.
- Проверено: приложение стартует, `/dashboard/login` → 200, новых ошибок нет.

> ⚠️ **НЕ трогал намеренно:** `next.config.mjs` → `images.remotePatterns` содержит `*.vercel-storage.com` — это хостинг реальных картинок сайта (логотип и др., 15 ссылок). Удаление сломает изображения. Если хотите полностью уйти с Vercel Blob — нужна **отдельная миграция ассетов** на своё хранилище/Supabase Storage, потом смена URL. Вынес в §7 как отдельную задачу.

## 3. Системные первопричины (чинить корень, а не симптомы)

| # | Корень | Какие находки порождает |
|---|---|---|
| R1 | `ignoreBuildErrors:true` + ESLint выключен | скрытые tsc-ошибки в `cached-dashboard.ts`, `label` в `ParsedTrack`, Date/string, `.details` без guard |
| R2 | Авторизация только per-route (нет `middleware.ts`), при копировании роутов забывают `require*` | F-SEC-1 (backups), F-SEC-2 (cookies), reports/quarters, мутирующие GET |
| R3 | Незавершённая миграция SQLite→Postgres | битые кнопки clear/delete, дубль страниц parsers, история в SQLite |
| R4 | Нет реляционной целостности (связи по строковому `artistId`, без FK) + несколько поколений форматов id | осиротевшие отчёты/выплаты, рассинхрон при удалении/переименовании |
| R5 | Нет единой стратегии на клиенте: ни AbortController, ни обработки 401, ни дизейбла на время запроса | гонки в аналитике, «зависшие» экраны при протухшей сессии, двойные сабмиты |
| R6 | Кэш (`unstable_cache` + ISR `revalidate=600`) без систематической инвалидации | цифры расходятся до 10 минут после мутаций |
| R7 | base64-данные в JSON и в БД (аватары, обложки) против узких лимитов схемы | сломанная загрузка аватара, раздувание ответов/БД |

## 7. Что могло пройти мимо / требует отдельной проверки

Эти пункты либо не проверяемы без прод-доступа, либо выходят за рамки диагностики кода — но важны:

1. **[env?] `AUTH_SECRET` на Timeweb** — если не задан, F-SEC-3 эксплуатируется тривиально. Проверить в панели Timeweb env.
2. **[env?] Роль в `DATABASE_URL` и режим pooler** — от неё зависит, работает ли RLS-миграция (F-INF-5) и не конфликтует ли pgbouncer transaction-mode с prepared statements `adapter-pg`. Проверить, что это owner-роль и порт/режим.
3. **[env?] Собирается ли `sqlite3` в прод-образе** (F-PARS-10) — локально нет. Проверить `/api/parsers/history` на живом Timeweb.
4. **Ассеты на Vercel Blob** (`*.vercel-storage.com`) — сайт зависит от чужого хостинга картинок. Нужна миграция на своё хранилище, иначе «уход с Vercel» неполный.
5. **Секреты в git-истории** (SECURITY.md прямо предупреждает) — проверить, не коммитились ли `.env`, VK/SFTP/Pyrus/DB ключи; при необходимости `git filter-repo` + ротация.
6. **Логаут не инвалидирует сессию на сервере** (stateless) — нельзя принудительно разлогинить скомпрометированного пользователя до ротации секрета.
7. **Нет reset-пароля** — единственный путь восстановления утерянного пароля артиста (в т.ч. после F-UI-12) — ручная правка админом.
8. **Конкурентное редактирование в двух вкладках** — last-write-wins без оптимистичных блокировок (артист/релиз/отчёт). Не проверялось глубоко.
9. **Реальные лимиты тела запроса** для base64-аватаров/обложек в Next route handlers на Timeweb (за прокси) — возможны обрезки/413.
10. **Гиганты-компоненты** (`playlists/page.tsx` 2060 строк, `settings` 687, `artists/[id]` 794) — не пройдены строка-в-строку; вероятны ещё гонки/утечки внутри. Требуют декомпозиции для надёжного аудита.
11. **Мобильная адаптивность** — [LIVE] заголовки страниц обрезаются справа на узком вьюпорте; полноценный аудит верстки/a11y не проводился.
12. **`instrumentation.ts` / scheduler** — при `ENABLE_IN_PROCESS_SCHEDULER=true` в проде появляется второй планировщик рядом с системным cron (риск двойных запусков). Проверить, что на Timeweb включён ровно один механизм.
13. **Обработка ошибок Supabase Storage** — загрузки обложек/бэкапов при недоступности бакета не проверялись на устойчивость.
14. **Excel-экспорт** (`/api/excel/[artistId]`) — корректность/большие объёмы не тестировались.
