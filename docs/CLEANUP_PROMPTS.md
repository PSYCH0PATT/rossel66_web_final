# Промпты для глубокой чистки проекта (Claude Code, Opus 5)

Три фазы. **Не склеивать в одну** — фаза 1 читает, фаза 2 удаляет.
Между фазами вы смотрите отчёт и вычёркиваете то, что трогать нельзя.

Настройки сессии: `/model opus`, effort **xhigh** для фаз 1–2.

---

## ФАЗА 1 — АУДИТ (read-only, ничего не удаляет)

```
Проведи полный инвентаризационный аудит этого репозитория. Это read-only задача:
на этом шаге не удаляй, не перемещай и не редактируй ни одного файла. Единственный
результат — отчёт docs/CLEANUP_AUDIT.md.

КОНТЕКСТ ПРОЕКТА (проверено, можешь не переоткрывать):
- Next.js App Router + Prisma (19 моделей) + Python-парсеры
- ~90k строк TS/TSX: app 30.7k, lib 20.4k, components 16.7k, scripts 10.5k
- 91 API route, 47 страниц, 71 prod-зависимость
- В git 1470 файлов, из них ~581 подходят под шаблоны мусора
- Известная проблема: сосуществуют два слоя хранения — Prisma (~72 файла)
  и lib/storage.ts (~47 файлов, 1173 строки). Похоже на недоделанную миграцию.
- Известная проблема: ARCHITECTURE.md (360 строк) ни разу не упоминает Prisma
  и описывает архитектуру, которой, судя по коду, уже нет.

ЧТО НУЖНО НАЙТИ. Для каждого пункта — полный список путей, а не примеры:

1. АРТЕФАКТЫ И МУСОР В GIT
   Дампы (parsers/zvonko_release_*.html и *_data.json), *.db в корне,
   backups/, data_backup_*, chrome_profiles/, venv_selenium/, test_env/,
   логи, *.doc/*.xlsx в корне, файлы с битыми именами
   (например начинающиеся с `{"success":false`), корневые test.ts…test9.ts,
   test-*.ts, debug_*.html, deploy-logs-*.
   Для каждого: отслеживается ли в git, есть ли ссылки из кода.

2. МЁРТВЫЙ КОД
   - экспорты, на которые нет ни одного импорта
   - файлы, в которые никто не входит по графу импортов от точек входа
     (app/**/page.tsx, app/**/route.ts, app/layout.tsx, скрипты из package.json,
     prisma seed, крон из crontab)
   - React-компоненты, которые нигде не рендерятся
   - закомментированные блоки длиннее 20 строк
   - код за флагами, которых нет в .env.example
   Отдельно помечай динамические импорты, реэкспорты через index-файлы и
   строковые ссылки — там статический анализ врёт чаще всего.

3. ДУБЛИ И ПАРАЛЛЕЛЬНЫЕ РЕАЛИЗАЦИИ
   Главный вопрос: разбери границу Prisma и lib/storage.ts. Какие сущности
   лежат где, где они пересекаются, какие API routes ходят в оба, где есть
   риск рассинхрона данных. Также: дублирующиеся утилиты, копипаст-хелперы,
   несколько версий одного парсера.

4. ЗАВИСИМОСТИ
   Из 71 prod-зависимости: какие не импортируются нигде; какие тянутся только
   из мёртвых файлов; какие стоят в dependencies, а нужны только в dev.

5. МАРШРУТЫ И СХЕМА
   API routes, на которые нет вызовов ни с фронта, ни из скриптов, ни из крона.
   Модели и поля Prisma, которые не читаются и не пишутся нигде в коде.

6. ДОКУМЕНТАЦИЯ
   Все *.md в корне и docs/: что описывает реальность, что устарело, что дублирует.

ФОРМАТ ОТЧЁТА
Таблицы, сгруппированные по шести разделам выше. Колонки:
путь | что это | доказательство (конкретные grep-находки или отсутствие ссылок) |
уверенность SAFE / LIKELY / RISKY | предлагаемое действие | что сломается, если ошиблись.

- SAFE  — доказано статически, обратных ссылок нет вообще
- LIKELY — ссылок не видно, но есть динамика/строковые пути/рефлексия
- RISKY — подозрительно, но нужен человек

Сообщай обо всём, что нашёл, включая мелочи и спорное. Не фильтруй по важности
и не отсекай неуверенные находки — фильтровать буду я на следующем шаге.
Именно поэтому нужна колонка с уверенностью.

В конце отчёта — раздел «Порядок удаления»: в какой последовательности это
безопасно сносить, что от чего зависит, где нужен прогон тестов между шагами.

ГРАНИЦЫ ЗАДАЧИ
Сделай ровно это и в этом объёме. Не рефакторь, не исправляй баги, не
переформатируй, не переименовывай, не правь типы, не улучшай архитектуру —
даже если видишь очевидные проблемы. Про такие находки напиши отдельным
списком «Замечено, но не входит в задачу» в конце отчёта.
Рутинные решения принимай сам; спрашивай меня только если разные прочтения
задачи ведут к существенно разной работе.

Субагентов используй только для широкого параллельного обхода дерева файлов,
максимум 4 штуки, и не используй их, чтобы перепроверять свою же работу.

Длина отчёта — по существу. Покрой содержание, но без воды, без повторных
резюме и без вводных разделов «о проекте».
```

## ФАЗА 2 — ЧИСТКА (выполняется после того, как вы прочли отчёт)

Перед запуском: `git checkout -b cleanup/deep-clean`. Рабочее дерево чистое —
неотслеживаемым остаётся только `tmp/`, это мусор и он уходит на шаге 1.

Промт переписан после аудита: раньше он диктовал шесть шагов, придуманных до того,
как отчёт существовал. Теперь единственный источник последовательности — раздел
«Порядок удаления» в самом отчёте, где шаги выведены из реальных зависимостей.

Запускать **не одним заходом**. План одобряется целиком, а шагов девять, с прогонами
между ними. Разумные подходы: шаги 1–2, потом 3–4, потом 5, потом 6. Каждый шаг —
свой коммит, откатываться есть куда.

```
Выполняем чистку по docs/CLEANUP_AUDIT.md.

Последовательность бери из раздела «Порядок удаления» в конце отчёта — он
единственный источник порядка. Не придумывай свою последовательность и не
переставляй шаги: зависимости между ними реальные. Например, 20 пакетов из
раздела 4.3 до шага 3 формально «используются», и удалять их раньше нельзя.

Я вычеркнул из отчёта то, что трогать нельзя — ориентируйся на актуальную
версию файла, а не на то, что помнишь.

Что можно удалять:
- SAFE — да, это основа работы.
- LIKELY — только если пункт назван поимённо в «Порядке удаления» и там
  объяснено почему. Все остальные LIKELY не трогай.
- RISKY — никогда, без исключений.
- Стоп-лист в начале «Порядка удаления» обязателен к исполнению. Там есть
  вещи, которые статический анализ считает мёртвыми, а они живые: ambient-типы
  без входящих импортов, маршруты, которые зовёт CI по URL из секрета,
  ops-ручки из runbook.

Отдельный git-коммит на каждый шаг, атомарно и с осмысленным сообщением.
Прогоны после каждого шага указаны в самом «Порядке удаления» — там же
помечено, где автотестов нет и нужна ручная проверка. Про такие места
напиши мне отдельно: я проверю руками, прежде чем ты пойдёшь дальше.

Если прогон падает — откати последний коммит, разберись, и продолжай.
Не чини падение дополнительными правками в коде: цель — удаление, а не
починка.

Слой хранения НЕ трогай — это отдельная задача. Учти поправку из раздела 0
отчёта: lib/storage.ts не второе хранилище, а фасад над Prisma, и проблема
там в обходе побочных эффектов, а не в дублировании данных.

Границы: только удаление и перемещение по списку. Никакого рефакторинга,
переименований, изменения логики или форматирования. Сужение экспортов
(шаг 7) — отдельный заход, в эту сессию не тащи.
Если по ходу видишь, что пункт из отчёта на самом деле небезопасен —
пропусти его и добавь в итоговый список пропущенного с объяснением. Это
ценнее, чем выполнить план дословно.

В конце: что удалено (счётчиком, не списком путей), сколько строк ушло,
что пропущено и почему, зелёный ли билд, какие шаги остались невыполненными.
```

## ФАЗА 3 — ЧЕСТНАЯ ДОКУМЕНТАЦИЯ

Выполняется **после** фазы 2: до неё половина того, что придётся описывать, будет удалена.

Формулировки про слой данных переписаны после аудита. В первой версии промта стояло
«Prisma и lib/storage.ts как два сосуществующих механизма» — это оказалось неверно
(раздел 0 отчёта), и, оставь мы строку как есть, новый ARCHITECTURE.md унаследовал бы
ровно ту ошибку, ради исправления которой его и переписывают.

```
Перепиши ARCHITECTURE.md и AGENTS.md с нуля, восстановив архитектуру из кода,
а не из существующих документов. Старый ARCHITECTURE.md устарел — используй его
только как источник вопросов, а не фактов, и не переноси из него ни одного
утверждения без подтверждения в коде.

docs/CLEANUP_AUDIT.md можно использовать как источник установленных фактов —
там у каждого утверждения есть доказательство. Но это снимок на момент прогона,
а после чистки часть его неверна: любое число (сколько маршрутов, моделей,
зависимостей) пересчитывай сам, не переписывай из отчёта.

ARCHITECTURE.md — что реально есть:
- слои и как запрос проходит от страницы до данных
- слой данных, точно:
  * база одна — Postgres через Prisma. lib/storage.ts не второе хранилище,
    а фасад над Prisma: он импортирует prisma и не делает ни одного обращения
    к файловой системе. Рассинхрона данных между ними быть не может.
  * у функций записи в lib/storage.ts есть два побочных эффекта, которых нет
    у прямого вызова Prisma: ревалидация ISR-кэша и постановка в очередь
    зеркала Buildin. Опиши это явно — здесь настоящая граница слоя.
  * механизмы хранения, которые действительно отдельные: SQLite-файлы
    парсеров (bandlink_playlists.db, vk_playlists.db) — их пишет Python,
    читает TS; и живые JSON-файлы в data/ (статусы парсеров, releases.json,
    backups.json, sftp_sync_index.json). Остальное в data/ — легаси.
  * статус парсеров хранится тремя способами одновременно: JSON-файлы,
    модель Prisma, SQLite с мостом. Опиши как есть, не как должно быть.
- API routes, сгруппированные по доменам, по одной строке на группу
- Python-парсеры: что делают, чем запускаются, куда пишут; и то, что скрипт
  и файл базы выбираются строкой в рантайме по платформе
- внешние интеграции (Buildin, Pyrus, Supabase Storage, SFTP) и какие
  переменные окружения им нужны
- что здесь легаси и находится в процессе миграции

AGENTS.md — рабочая инструкция для ИИ-агента в этом репозитории:
- карта директорий: что где лежит
- какой слой данных канон для новых фич, а какой не трогать
- как запускать: dev, build, тесты, парсеры
- конвенции, которые видны в коде (не выдумывай)
- ловушки: места, где легко сломать что-то неочевидно. Как минимум эти,
  все подтверждены в отчёте — проверь, что они ещё актуальны:
  * запись в обход lib/storage.ts теряет ревалидацию ISR и зеркало Buildin.
    Уже есть доказанные обходы: подтверждение отчёта, создание отчётов из
    трёх маршрутов, удаление отчётов без архивации.
  * переименование экспорта StreamingChart молча ломает график в рантайме
    без ошибки типов: он извлекается строкой внутри динамического импорта.
  * ENABLE_IN_PROCESS_SCHEDULER=true в .env.example соседствует с системным
    crontab — парсеры запускаются дважды.
  * в миграциях нет CREATE TABLE для StreamAnalytics, поэтому
    prisma migrate deploy на пустой базе падает.
  * types/*.d.ts не имеют входящих импортов по устройству — они не мёртвые.
Сохрани существующий блок OPENSPEC между маркерами без изменений.

Каждое утверждение должно опираться на конкретный файл. Если чего-то не
можешь установить из кода — пиши «не установлено», а не догадку. Если код
противоречит отчёту — прав код, и скажи мне об этом отдельной строкой.

Длина по делу: AGENTS.md должен целиком помещаться в контекст без сожалений,
ориентир 150–250 строк. ARCHITECTURE.md — сколько нужно, но без заполнителей.
```

## Почему промпты написаны так (гайд Anthropic по Opus 5)

Что **специально не** написано в промптах выше и почему:

| Не пишем | Причина |
|---|---|
| «перепроверь себя», «сделай финальную верификацию» | Opus 5 верифицирует себя сам. Такие фразы вызывают избыточную перепроверку: лишние токены и время, без выигрыша в качестве. |
| «сообщай только о критичном», «будь консервативен» | Модель поймёт буквально и найдёт меньше. Правильно — просить сообщать всё и фильтровать отдельным проходом. Поэтому в фазе 1 стоит колонка уверенности. |
| «double-check перед ответом» | То же самое: самокоррекция уже встроена, инструкция только удорожает. |

Что **специально есть**:

- **Полное ТЗ сразу, одним куском.** Opus 5 сильнее всего на длинных агентных задачах, когда получил всю спецификацию заранее и его не дёргают.
- **Явные границы задачи.** Модель склонна расширять scope и «заодно» чинить то, что не просили. Для чистки это опасно, поэтому границы прописаны отдельным абзацем.
- **Лимит субагентов.** Opus 5 делегирует охотно; на широком обходе дерева это уместно, но без потолка множит стоимость.
- **Калибровка длины отчётов.** Файлы, которые Opus 5 пишет на диск, по умолчанию длиннее, чем нужно.
- **Разделение чтения и удаления.** Не из-за модели, а из-за необратимости: между фазами вы читаете отчёт.
