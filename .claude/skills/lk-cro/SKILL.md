# LK-CRO — конверсионно-иерархический аудит личных кабинетов

CRO для дашборда ≠ CRO для лендинга. Здесь никто ничего не «покупает» — конверсия ЛК измеряется тем, как быстро пользователь решает свою задачу и насколько экран не мешает ему это делать. Этот скилл разбирает экраны ЛК по одному и выдаёт решения: что главное, что убрать, что спрятать.

## Контекст продукта

rossel-music — платформа музыкального лейбла/дистрибуции. Два ЛК:

- **Админ-ЛК** (`app/dashboard/admin/*`) — внутренний инструмент команды лейбла. Экраны: дашборд, релизы (+ парсеры Zvonko/Koala, привязка), артисты (+ bulk-добавление), аналитика (стримы по площадкам), плейлисты, отчёты, выплаты, активность, настройки.
- **Артист-ЛК** (`app/dashboard/artist/[username]/*`) — кабинет артиста лейбла. Экраны: дашборд, релизы, аналитика, плейлисты, отчёты, выплаты, настройки.

Оптимизационная цель РАЗНАЯ, это главная развилка скилла:

| | Админ | Артист |
|---|---|---|
| Кто | Оператор, живёт тут ежедневно | Гость, заходит редко |
| Цель экрана | Скорость: частые задачи за минимум кликов, bulk-операции, поиск | Ясность: главные цифры и статусы сразу, ноль обучения |
| Смертный грех | Частое действие спрятано, редкое — торчит | Внутренний жаргон (парсеры, UPC, привязки), перегруз |
| Метрика успеха | Кликов/секунд до топ-3 задач | «Понял всё за 5 секунд без вопросов» |

## Входные данные (без них аудит не начинать)

1. Скриншоты экрана: desktop 1440 и mobile 390. Оценка UI только по скринам, никогда только по коду. Если скринов нет — сначала снять (Playwright / design-review агент).
2. Роут и роль (админ/артист).
3. От пользователя: топ-3 реальные задачи на этом экране и частота («каждый день / раз в квартал»). Если не знает — спросить, не выдумывать.

## Процесс: 5 шагов на каждый экран

### Шаг 1. Job экрана — одна фраза
«Админ приходит сюда, чтобы ___». Не получается одной фразой — экран делает слишком много, это уже само по себе finding.

### Шаг 2. Полная опись элементов
Перечислить ВСЁ: кнопки, табы, фильтры, карточки метрик, колонки таблиц, блоки. Каждому элементу — оценка `частота использования × важность для job`:

- **PRIMARY** — служит главной задаче, используется постоянно. Лимит: 1 действие + 1 метрика/сущность на экран.
- **SECONDARY** — нужно регулярно, но не главное.
- **RARE** — нужно раз в месяц/квартал (импорты, bulk, экспорт, тех. операции).
- **DEAD** — никто не использует / дублирует другое / осталось от старой фичи.

### Шаг 3. Правила размещения (жёсткие)
- PRIMARY: одна выделенная кнопка (единственная filled на экране) + главная метрика первой. Всё остальное визуально тише.
- SECONDARY: outline/ghost рядом или в Toolbar.
- RARE: убрать с поверхности — dropdown («Импорт», «Ещё»), отдельная страница или настройки. Пример: Zvonko Parser + Koala Parser + «Привязать релизы» = три RARE-кнопки, торчащие рядом с primary → один dropdown «Импорт».
- DEAD: удалить. Не прятать — удалить (git всё помнит).
- Визуальный вес = частота×важность. Если редкая кнопка ярче частой — это баг иерархии, main finding.

### Шаг 4. Friction-чек
- Сколько кликов до каждой из топ-3 задач? Больше 2 для ежедневной задачи админа — finding.
- Mobile 390: что-нибудь перекрывает данные? (тултипы/оверлеи графиков — рендерить фиксированной панелью под графиком, не поверх). Горизонтальный скролл, недоступные действия — findings.
- Первый экран без скролла: видна ли главная метрика и primary-действие?
- Состояния: пустое (что видит новый артист без релизов?), загрузка, ошибка. Отсутствие внятного empty state — finding.
- Для артист-ЛК: пройтись глазами новичка (cognitive walkthrough) — каждый ярлык понятен без знания внутренней кухни? Термины админки на экране артиста — critical.

### Шаг 5. Вердикт
Выдать по шаблону (см. ниже) + приоритет ICE (Impact/Confidence/Ease, 1–10). Решения дописывать в `docs/ia-decisions.md` — это журнал, следующие сессии читают его, чтобы не перерешивать заново.

## Сквозные проверки (между экранами)

- Одинаковые сущности выглядят одинаково на всех экранах (карточка релиза в админке == в артист-ЛК с поправкой на роль).
- PageHeader/Toolbar/отступы идентичны на всех страницах — любое расхождение finding.
- Одно и то же действие называется одним словом везде.
- Порядок пунктов сайдбара = частота использования, роль в роль.

## Шаблон выходного отчёта (на экран)

```markdown
## /dashboard/admin/releases — [роль: админ]
**Job:** быстро находить релиз и добавлять новые
**Primary action:** Добавить релиз · **Primary metric/entity:** таблица релизов + поиск

| Элемент | Класс | Вердикт | Куда |
|---|---|---|---|
| Добавить релиз | PRIMARY | keep, единственная filled | на месте |
| Поиск | PRIMARY | keep, шире | на месте |
| Zvonko Parser | RARE | demote | dropdown «Импорт» |
| Koala Parser | RARE | demote | dropdown «Импорт» |
| Привязать релизы | RARE | demote | dropdown «Импорт» |
| Фильтры | SECONDARY | keep, ghost | на месте |

**Friction:** [находки]
**Mobile:** [находки]
**ICE-приоритет изменений:** [список]
```

## Анти-правила

1. Не добавлять новые элементы во время decluttering-прохода. Только keep/demote/move/kill.
2. Не прятать то, что пользователь назвал ежедневной задачей, ради «чистоты».
3. Не менять логику/данные/API — только представление и размещение.
4. Не оценивать красоту — это задача design-review. Здесь только иерархия, шум, friction.
5. Сомнительный элемент (непонятна частота) — спросить пользователя, не гадать.
6. Внедрение решений — волнами по 2–4 экрана с visual diff против baseline, не всё сразу.
