# Передача проекта в облачную сессию Claude Code

**Кому:** Opus 5 в сессии на claude.ai/code.
**Репозиторий:** `PSYCH0PATT/rossel66_web_final`, рабочая ветка **`redesign/design-system`** (всё запушено, локальных хвостов нет).
**Задача сессии:** выполнить ОДИН пункт плана — тот, который владелец назвал в стартовом сообщении. Не больше.

> **Правило номер один: одна сессия = один пункт.** Не «пройти план», не «сделать заодно следующий». Выполнил свой пункт, довёл до критерия готовности, закоммитил, отчитался — на этом сессия закончена. Следующий пункт владелец запустит новой сессией со свежей VM. Это не бюрократия: контекст, размазанный на несколько этапов, — главная причина тихих ошибок в этом проекте.

## 2. Что делаешь САМ, без вопросов

### 2.1 Проверка среды (первым делом, до любой работы)

Выполни и отчитайся одним блоком:

```bash
pnpm install
pnpm verify --fast
psql --version   # PostgreSQL 16 предустановлен в облачных сессиях
```

Стенд поднимаешь так (в порядке предпочтения):
1. `docker compose -f docker-compose.test.yml up -d` — в облаке Trusted-доступ включает Docker Hub, должно работать.
2. Если реестр недоступен (`Forbidden` при pull) — **не мучайся с докером**: подними нативный постгрес: `service postgresql start`, создай базу/пользователя с кредами из `docker-compose.test.yml` (rossel/rossel/rossel_test) на порту **54329**, дальше `pnpm test:db:migrate` и `pnpm seed:e2e`.
3. Что выбрал — допиши в `docs/baseline-issues.md`, чтобы следующие сессии не выясняли заново.

### 2.2 Свой пункт — и только он

Владелец в стартовом сообщении называет пункт (например «Б3» или «чат 11»). Находишь его промпт в `PROMPTS_PLAYBOOK.md`, выполняешь целиком, доводишь до критерия готовности, коммитишь и пушишь. Внутри своего пункта разрешения не спрашиваешь — он уже согласован.

Закончив — **останавливаешься**. Не начинаешь следующий пункт, даже если он выглядит мелким и «логично сразу сделать». Если владелец в этой же сессии просит доделать/починить твой пункт — доделываешь здесь же; новый пункт = новая сессия.

**Исключение — план перед правками.** Для пунктов 10–12 (иерархия) сначала показываешь план по каждому экрану и ЖДЁШЬ подтверждения владельца: там перестановки с изменением логики.

### 2.3 Правила, которые нарушать нельзя

1. **Скриншоты — в рамках одной сессии.** VM свежая, `screens/` в gitignore, эталона между сессиями нет. Поэтому: сними `before` ПЕРЕД правками (`pnpm visual:baseline --routes <роуты> --out screens/before`), сделай правки, сравни (`pnpm visual:diff screens/before screens/after`).
2. **Не смотри скриншоты пачками.** Дифф читаешь как текст (проценты). Открываешь картинку глазами ТОЛЬКО для экрана, где расхождение выше порога и причина не выводится из твоих же правок. Это прямое требование экономии — каждое изображение дорого.
3. **Критерий готовности не на слово, а проверкой.** Если объясняешь расхождение — докажи прогоном (два прогона на одном коде / откат файлов / изоляция), а не рассуждением. В этом проекте уже был случай, когда правдоподобное объяснение оказалось неверным.
4. **Волны миграции представление не меняют по смыслу** — только вёрстка на компоненты. Логику/API/данные трогают только чаты 10–12 и только по вердиктам из `ia-decisions.md`. Ни одного изменения, которого нет в документе.
5. **Каждый пункт заканчивается commit + push.** Дерево между пунктами — чистое (`git status`).
6. **Никаких «заодно».** Нашёл постороннее — в `docs/backlog.md` и дальше по скоупу.
7. **Не мержить в staging.** Финал (чат 13) готовит merge и останавливается.

### 2.4 Что ещё делаешь сам, если пригодится

- Составляешь точный список недостающих env-переменных (см. ниже) — по факту падений, а не по догадке.
- Если что-то в документах устарело относительно кода — правишь документ и говоришь об этом в отчёте.
- Если пункт плейбука упирается в невозможность (нет доступа, не поднимается стенд) — не имитируешь результат: пишешь владельцу, что именно нужно, и берёшься за следующий пункт, который не заблокирован.

## 3. Что владелец должен сделать РУКАМИ (ты не можешь)

Проверь, что это сделано; чего нет — попроси одним списком в первом же ответе, не растягивая на несколько сообщений.

**3.1 Подключить GitHub** — авторизовать Claude GitHub App при онбординге на claude.ai/code (или `/web-setup` в терминале), чтобы сессия видела `PSYCH0PATT/rossel66_web_final`.

**3.2 Выбрать ветку `redesign/design-system`** при создании сессии — НЕ main/staging.

**3.3 Настроить облачное окружение** — иконка облака над полем ввода на claude.ai/code → шестерёнка:

- **Network access:** `Trusted` (включает npm, GitHub, Docker Hub). Менять на Custom не нужно.
- **Environment variables** (формат `.env`, по строке на переменную) — значения владелец берёт из своих локальных `.env.local` / `.env.e2e`, которые в git не лежат. Минимально нужны для сборки и тестов:
  `DATABASE_URL`, `DIRECT_URL`, `TEST_DATABASE_URL`, `AUTH_SECRET`, `CRON_SECRET`, `FORM_DELIVERY_ENCRYPTION_KEY`, `NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_BASE_URL`, `INTERNAL_CRON_BASE_URL`, `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `SHOW_TEST_ACCOUNTS`, `ENABLE_IN_PROCESS_SCHEDULER`, `BUILDIN_DUAL_WRITE`, `PYRUS_WRITE_DISABLED`
  Внешние интеграции (SFTP_*, PYRUS_*, BUILDIN_*, VK_*, YANDEX_*, SENTRY_*) для UI-работы не нужны — добавлять только если что-то реально упадёт.
- **Setup script** (выполняется один раз, потом кешируется снапшотом):
  ```bash
  #!/bin/bash
  set -e
  corepack enable && corepack prepare pnpm@latest --activate
  pnpm install --frozen-lockfile
  docker compose -f docker-compose.test.yml pull || true
  ```

**3.4 Приёмка волн.** Владелец смотрит превью на телефоне и отдельно прогоняет визуальную приёмку в своей Cowork-сессии. Для админ-экранов ему нужна админ-сессия в Chrome, для артистских — аккаунт артиста.

**3.5 Решения, которых нет в документах.** Все 8 вопросов по вердиктам уже закрыты (см. раздел 4 в `ia-decisions.md`). Если всплывает НОВАЯ развилка — спрашиваешь владельца, не решаешь сам.

## 4. Формат отчёта после каждого пункта

Коротко и по делу:
1. Что сделано (пункт плейбука + суть).
2. Проверки: тесты / smoke / visual-diff — цифрами.
3. Коммит и ветка.
4. Что требуется от владельца (если требуется) — отдельным списком.
5. Что дальше по плану.

Не пересказывай содержимое файлов, владелец их читал. Не пиши «готово», пока критерий готовности пункта не выполнен проверкой.

## 5. Как начинается каждая сессия

Владелец даёт этот файл и называет пункт. Твой первый ответ — всегда одинаковый ритуал:

1. Прочитал документы из раздела 0 (и конкретно промпт своего пункта в `PROMPTS_PLAYBOOK.md`).
2. Проверил среду (2.1) — коротко: что поднялось, что нет.
3. Чего не хватает от владельца (если не хватает) — одним списком.
4. Что именно собираешься сделать в этом пункте.

И только после этого начинаешь работу. Если пункт не назван — спроси, какой, и не выбирай сам.
